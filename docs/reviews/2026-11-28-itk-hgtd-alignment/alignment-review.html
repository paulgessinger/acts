Assessment

A credible route, with specific missing connections

Build the shared alignment mathematics on ACTS, and retain Athena’s experiment-specific geometry, optimizer adapter and conditions ownership. The source supports this direction. It does not yet establish a complete ACTS-based ITk alignment workflow that estimates constants, persists them, reloads them and closes on independent reconstruction.

Implemented pieces

ITk conditions reach ACTS

Athena converts Pixel/Strip alignment stores into the geometry context used by ACTS surfaces. Reuse and validate this path.

Recommended first demonstrator: recover a controlled ITk displacement using ACTS-derived alignment contributions and the ATLAS optimizer; write the correction through Athena conditions; restart reconstruction and validate on held-out events. Start with a small, constrained parameter set including Pixel and Strip.

In parallel, make one HGTD module displacement survive a payload write/read cycle and appear identically in readout geometry and ACTS. Reuse the same contribution contract for the subsequent spatial solve.

This assessment distinguishes consuming alignment constants, estimating them from tracks, and demonstrating a complete correction loop. A working geometry context, a solver return code, or a telescope result proves only part of the chain.

Why changing the fitter property is insufficient

The legacy preprocessor calls IGlobalTrackFitter::alignmentFit and expects AlignmentCache to contain a derivative matrix and full covariance. ActsToTrkFitterWrapTool implements the ordinary ITrackFitter interface and returns a converted Trk::Track; that does not supply the alignment cache.

IGlobalTrackFitter alignment contract · BeamspotVertexPreProcessor alignment refit · ordinary ACTS fit and Trk conversion

Possible compatibility bridge

Implement the exact legacy alignment cache from ACTS, including track-state ordering and covariance semantics. This could help comparison with the old chain, but carries substantial coupling to legacy track/fitter internals.

Preferred contribution adapter

Expose the reusable mathematical result from ACTS and adapt it at Athena’s matrix boundary. Keep detector bookkeeping and conditions in Athena, while avoiding legacy track objects throughout the ACTS alignment layer.

Concrete implementation caution: scalar MatrixTool::addFirstDerivative and addSecondDerivative are implemented; several plural overloads are empty. MatrixTool also needs AlignPar/IAlignModuleTool identities, hit/track counts, scaling and output metadata. This is an adapter project, not simply two function calls.

ACTS’s current alignment evaluator owns a Kalman refit and vector track container. Reviewer detail: gradient, Hessian and fitted-track correlations

Use V for measurement covariance, Q for the fitted prediction covariance in measurement space, D for the alignment derivative and r for the matched residual vector. Define R = V − Q and W = V⁻¹ R V⁻¹.

ACTS:   g = 2 Dᵀ W r
Legacy: g = 2 Dᵀ V⁻¹ r
Both Hessian forms: H = 2 Dᵀ W D
Difference: g_ACTS − g_legacy = −2 Dᵀ V⁻¹ Q V⁻¹ r

The difference vanishes if Q V⁻¹ r = 0 (or after its projection by the alignment derivatives). A converged, unconstrained linear least-squares problem can satisfy this through its normal equations. Material priors, seed constraints, omitted pseudo-measurements, differing cuts and incomplete convergence can invalidate hit-only orthogonality.

In ACTS, Q = P C Pᵀ uses a bound-state-to-measurement projector and the fitted cross-state covariance. Do not confuse P with the global track design matrix of a simple straight-line least-squares fit. The open #6217 discussion and merged #6215 pseudo-residual change make material-sensitive comparisons particularly relevant.

Acceptance for the first adapter

Construct one small problem with identical measurements, geometry, local-track/material model, linearization, gauge, priors and outlier decisions. Compare reduced equations and right-hand side before comparing corrections. Exercise a zero-shift case, a known shift, rotated/strip measurements and material-sensitive tracks. Compare against finite differences. A thin, straight telescope alone will not settle all of these questions.

Keep backend capabilities explicit. ATLAS matrix policy, Mille pseudo-measurements and the ACTS dense reference solver may differ internally; each adapter must preserve the agreed problem rather than silently adding or dropping constraints.

H8 — ACTS HGTD PlaneSurface and store-aware transform
Do not mistake the misalignment example for an application test

The reviewed generator produces zero, constant or Gaussian translations in module payloads. ApplyRotation and ApplyToGeometry are exposed but unused in its implementation; rotations are zero. Diagnostics add quantities labelled local shifts directly to global centre coordinates. They therefore do not certify the intended moved transform or local/global convention.

execute() gates writing on WriteToDB, while finalize() unconditionally writes and registers output. These are reasons to repair and validate the prototype before relying on it, not claims that an observed job failed.

A spatial residual path that preserves the track uncertainty

The current HGTD calibrator constructs three-dimensional measurements: local x, local y and time. The CKF extension starts at an ITk track state, uses HGTD hits in its updates and chooses branches by chi-square. Those states are useful inputs, but their residuals are not independent residuals against a fixed ITk reference.

H10 — HGTDTrackExtensionAlg ITk starting state and CKF · H11 — OnTrackCalibrator 3D HGTD projector and time units · H19 — HGTD extension configuration, 3D measurement selection
  1. Start with ITk-only reference tracks. Extrapolate without HGTD updates. Select the two spatial measurement rows explicitly and hold timing calibration fixed. Keep matching stable for derivative checks, then measure its change in closure.
  2. Preserve correlations. Include propagated ITk covariance and material uncertainty. Residuals at different HGTD layers share the ITk uncertainty: use their joint covariance or a track-local nuisance model with one ITk prior. Do not add the same prior independently for every hit.
  3. Constrain the first solve. Fix ITk geometry and begin with a defined rigid endcap/disk group. Test the best-conditioned transverse translations and normal-axis rotation first. Release longitudinal motion and tilts only after checking rank, angular coverage and correlations.
  4. Persist module corrections. The current HGTD manager/DB APIs are module based and ignore the hierarchy-level argument. A group correction must be composed into module-frame deltas or require a new conditions representation. Equal local shifts on differently oriented modules are not a global rigid shift.
  5. Validate independently. Recover injected observable modes on held-out events, check residual means/pulls, associations and timing stability. An HGTD-to-ITk solution inherits ITk weak modes; joint ITk+HGTD alignment is a later milestone.

These are proposed integration and validation steps. They are not an existing HGTD alignment workflow in the reviewed configuration.

Keep spatial and timing milestones distinct. ACTS’s alignment state builder uses the calibrated measurement dimension and projector dynamically, so a generic 1D/2D-only restriction was not found there. However, its path derivative keeps spatial direction and leaves the time derivative zero under a local linear-track approximation. A 3D measurement alone does not establish validated coupled space/time derivatives. Check all enabled spatial motions in the chosen field/material propagation; address path-length/time coupling explicitly before a joint fit.

Implementation sequence

Prioritize closure over another isolated demonstrator

The following gates are recommendations. They specify deliverables and evidence, not promised dates or accepted assignments. Geometry/conditions work and the mathematical-contract prototype can proceed in parallel.

Gate 0 · reproduce and define

Freeze one small reference problem

Capture exact SHAs, geometry/tag, conditions folders/IOVs, input sample, fitter/material settings, active parameters and gauge. Reproduce the legacy ITk accumulation/solve and an ACTS alignment example. Inventory external/private work with its executable recipe and output evidence.

Proposed owners: integration lead, Athena alignment maintainers, ACTS fitting/alignment maintainers.

Exit: an executable manifest and baseline report, with explicit failures if reproduction is incomplete. Select representative Pixel and Strip modules in barrel and endcap, then a small group.

Gate 1 · geometry and conditions

Make constants survive a fresh reconstruction

Resolve ITk output folder/tag/IOV configuration and enable a proven write path. Inject identity and signed translations/rotations; write, restart and compare expected surface origin/axes. Include split strips, annulus frames, a parent motion, unrelated surfaces and two IOVs. In parallel, add the HGTD conditions route and repeat the module test.

Proposed owners: Pixel/Strip/HGTD geometry and Athena conditions maintainers.

Exit: readout and ACTS transforms agree with the intended correction after readback; concurrent events follow their own IOV. Explicitly distinguish reconstruction-geometry mismatch tests from displaced Geant4 transport.

Gate 2 · contribution and adapter

Connect ACTS to the ATLAS matrix boundary

Agree the public contribution interface, stable parameter map, local-track/material model and gradient convention. Implement bounded accumulation into the scalar MatrixTool API with correct counts, scaling and solver metadata. Use #6607 or its agreed successor as the public API baseline.

Proposed owners: ACTS contribution API maintainer paired with ATLAS optimizer maintainer.

Exit: finite-difference agreement and matched small-problem gradient/Hessian/RHS checks; recover a known module correction, persist it and reconstruct held-out events. Include 1D strips and material-sensitive tracks early.

Gate 3 · hierarchy and HGTD spatial solve

Use the landed group machinery end to end

Wire selection/layout, structure derivatives, shared equation assembly and consistent member updates. Begin with disjoint groups and module selections. Add HGTD spatial residual extraction with a correlated ITk reference and compose group results into module payloads.

Proposed owners: ACTS hierarchy developers with ITk/HGTD mechanical geometry experts.

Exit: zero-shift and blind shifted-group closure with a documented gauge, member-transform round trip, rank diagnostics and held-out residual/track validation. Keep simultaneous parent/child and joint ITk/HGTD releases as explicit later extensions.

Gate 4 · independent backend and scale

Establish operational evidence

Compare optional Mille/Pede on the same small statistical problem after resolving relevant representation issues. Then grow occupancy and parameter count; test distributed accumulation, deterministic mappings, bounded memory, replay/relinearization, failure recovery and IOV concurrency.

Proposed owners: integration/validation lead and each backend maintainer.

Exit: correction bias/uncertainty coverage for observable modes, physics performance on independent samples, resource measurements and explicit unconstrained/weak-mode reporting. Demonstrate iteration convergence and reproducible regression workflows.

For a human review meeting

Decisions to make before implementation expands

  1. Accept the contribution adapter as the main route? Keep a legacy cache adapter only if it has a clearly bounded comparison purpose.
  2. Which statistical model is authoritative for the first test? Specify track-local elimination, material and seed priors, residual conventions and the expected gradient/Hessian. Resolve the difference highlighted above.
  3. Which parameter identities and physical groups are persisted? Agree frames, pivots, module/surface mapping and deterministic cross-job ordering; start with a constrained selection.
  4. Which payload folder/tag/IOV is the ITk output contract? Name the writer and fresh-reader recipe, including how effective group corrections become supported payload entries.
  5. What defines the HGTD first success? Conditions application first, then a relative spatial solve with fixed ITk reference and explicit shared track uncertainty.
  6. Who owns the complete loop? Name one integration lead across ACTS API/hierarchy, Athena optimizer, detector conditions and validation. Check any external prototypes before assigning duplicate work.

The first useful review outcome is a small set of tracked tasks with owners and executable exit criteria. The important milestone is a recovered correction that remains correct after persistence and fresh reconstruction.
